# 代码与架构审计（2026-08-11）

## 结论

项目的 provider plugin、账号租约、失败处置、操作事件和加密设置边界总体成立，适合继续作为模块化单体演进。本轮主要风险集中在“目录契约未执行”“管理操作缺少专用契约”和“前端已有 MUI 但未形成响应式设计系统”。

## 本轮修复项

| 严重度 | 问题 | 影响 | 处理 |
| --- | --- | --- | --- |
| P1 | 模型 token 限制只展示、不校验 | 请求可在本地已知超限时仍占用账号并触发上游失败 | 增加持久化覆盖、有效值合成和统一请求守卫 |
| P1 | 账号探测固定模型且复用短超时路径 | 无法定位单模型故障，生产入口可能 504 | 增加模型选择、真实输出和独立长任务端点 |
| P1 | `html/body`、主内容强制 1040/1280px | 移动端和窄屏无法使用，抽屉不可达 | 重做响应式 App Shell 和页面容器 |
| P2 | 账号点击跳转详情页 | 丢失筛选、分页和滚动上下文 | 列表内大尺寸详情弹窗，保留兼容路由 |
| P2 | 保活周期和 jitter 是全局魔法值 | 无法适配不同厂商凭据与风控节奏 | 增加按厂商加密运行策略 |
| P2 | `accounts.tsx`、`api.ts` 聚合过多职责 | 变更冲突和回归面持续扩大 | 本轮先抽离详情、探测和策略界面；API 后续按领域拆分 |
| P2 | `ProviderRegistry` 使用 `@Autowired` 区分生产构造器 | 违反项目构造器注入规范 | 改为单一生产构造器和显式测试工厂 |

## 视觉审计

当前视觉已使用 MUI，但固定桌面宽度、永久侧栏、重复 inline `sx` 和缺少统一空态/窄屏策略，使它更像内部原型。新基线采用：

- 224px 桌面导航与移动 temporary drawer；
- 56px 顶栏、最大 1600px 内容区、响应式 16/24/32px 页面边距；
- graphite/white/cool-gray 主体，teal 主操作，cobalt 辅助，绿色/琥珀/红色表达状态；
- 4–8px 圆角、1px 边框、极轻阴影、高密度 44–48px 表格行；
- 账号详情使用大工作弹窗，模型编辑使用中型任务弹窗，不使用装饰性卡片嵌套。

视觉概念保存在 `output/imagegen/any2api-*-concept.png`，仅作为布局和视觉语言依据，不作为运行时资产。

## 保留的后续债务

- `web/src/lib/api.ts` 应按 catalog/accounts/lifecycle/settings 领域拆分，并引入统一错误对象与可配置超时策略。
- 部分 overview 指标仍是占位文案，应由后端提供真实生命周期积压和自动化 lane 指标后再展示。
- Python provider 中存在为页面脚本兼容而保留的空 `catch`；需要逐个结合浏览器证据审计，不能机械删除。
- 精确上下文核算需要按模型 tokenizer registry；当前统一估算器应通过真实 usage 数据持续校准。
