# 全系统可靠性与桥接深度排查

## 目标

用户要求从 Arena 专项扩展为全系统排查，同时继续修复已有缺陷。以当前生产 1.5.8、Self Proxy 四节点为基线，查明失败、长等待、资源泄漏、慢读取和协议退化的原因，按严重度修复并完成可回滚交付。

## 范围

1. 生产：Kubernetes Pod/探针/资源/重启、数据库连接与慢查询、Redis 协调、调度队列和外部依赖。
2. Automation：Action 调度、同步/异步边界、浏览器预算与会话池、取消/超时/进程回收、代理引用和租约、凭据恢复。
3. Backend：账号调度与初次验证、重试/取消/幂等、流式状态与缓存、Chat/Responses 契约、管理 Read 查询与权限隔离。
4. Web：关键管理读取/错误恢复与请求取消，现有构建/类型/lint 门禁。
5. 全部启用厂商的适配静态检查与近期真实业务证据；不把模型目录或 HTTP 200 当作生成成功。

## 非目标与约束

- 不重启停用的 DeepSeek/Qwen，不恢复周期生成探活，不处理 RCM。
- 不新增外部 SaaS、人工验证管理 API、权限模型或无关重构；生产凭据只在受限文件、stdin 和内存中流转。
- 优先零生成诊断、已有流量及合成测试。必要的生成只做有明确验证目标的少量请求。
- 保留用户工作树；当前 1.5.9 Arena 会话/错误修复是本任务已有改动，整合交付。

## 交付与验收

- 报告按 P0/P1/P2 记录问题、直接证据、影响、已修复/待验证边界、测试和回滚点。推断与确定根因分别标识。
- 修复最相关的成功、失败、边界与取消/并发回归，再运行全量质量与版本门禁。
- 可部署候选统一占用 1.5.9；不覆盖 1.5.8 制品。后续接受候选后再修改源码必须继续升版本。
- 沿现有授权提交、CI、镜像/GitOps、Pod/digest/API 验证；真实有效输出单独验收。应用回滚至 1.5.8，不改回已停用的 HE IPv6 池。
- 影响文件随确认缺陷收敛，主要围绕 `automation/` 运行时、`backend/` 调度/推理/读取及 `deploy/gitops/`，Web 只处理与发现问题直接相关的改动。
